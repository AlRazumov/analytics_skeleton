# Контракт DataSourceAdapter: что проверяется

Для разработчика адаптера (Bitrix24Adapter, OneCAdapter и т.п.). Интерфейс —
`app/Core/Contracts/DataSourceAdapter.php`; ниже правила, на которые
опирается ядро и которые автоматически проверяет
`App\Adapters\Contract\AdapterContractChecker`.

## Как проверить

```bash
./vendor/bin/sail artisan adapter:check                          # три последних месяца
./vendor/bin/sail artisan adapter:check --period=2026-01:2026-03 # конкретные месяцы
```

Команда проверяет источник из `ANALYTICS_SOURCE`, только читает его (в БД
ничего не пишет), печатает объёмы данных, пропущенные правила и нарушения
с примерами (до 5 на правило). Код возврата 1 — есть нарушения.

Правила про повторяемость и границы (`*.repeatable`, `*.split`) предполагают,
что данные за период не меняются во время проверки, — берите закрытый
период, а не текущий день.

В тестах: мок проверяется в `tests/Unit/Adapters/Contract/AdapterContractCheckerTest.php`;
новый адаптер добавляется туда же тестом «passes …» на записанных ответах
источника (фикстурах), без сети.

## Правила

| Код | Что требуется |
|-----|---------------|
| `capabilities` | `capabilities()` — список `AdapterCapability` без повторов |
| `products.ids`, `warehouses.ids`, `sellers.ids` | id непустые и уникальные в справочнике |
| `products.names`, `warehouses.names`, `sellers.names` | названия непустые |
| `*.type` | методы отдают объекты нужного класса (`Deal`, `Product`, `StockBalance`…) |
| `deals.ids` | id сделки непустой и уникальный в одном вызове |
| `deals.range` | все сделки внутри запрошенного диапазона; обе границы `DateRange` включительно, по дате (время не важно) |
| `deals.amount` | сумма — конечное число (отрицательная допустима: возврат) |
| `deals.products` | `productId` сделки есть в `fetchProducts()` — справочник отдаёт и архивные товары |
| `deals.repeatable` | повторный вызов на том же диапазоне отдаёт те же сделки (id, товар, сумма, дата, продавец) — адаптер не держит состояние между вызовами |
| `deals.split` | сделки диапазона = сделки `[начало..D]` ∪ `[D+1..конец]`, и сделки дня D = выборке за `[D..D]` (ловит «конец не включительно», сдвиг часового пояса) |
| `sellers.on_deals` | `sellerId` сделки — `null` («без продавца») или id из `fetchSellers()`; не `''` и не зарезервированный `__none__` |
| `sellers.coverage` | `none` — ни у одной сделки нет `sellerId`; `full`/`partial` — продавец есть хотя бы у одной (сделки без продавца допустимы в обоих; см. `SellerCoverage`) |
| `movements.*` | то же для `fetchStockMovements()` (`ids`, `range`, `quantity`, `products`, `repeatable`, `split`); `movements.warehouses` — склад движения есть в `fetchWarehouses()`, если справочник складов не пуст. Только при capability `stock_movements` |
| `stock.pairs` | пара товар × склад встречается в одном вызове `fetchStock()` один раз |
| `stock.quantity` | остаток — конечное число (отрицательный не запрещён) |
| `stock.products`, `stock.warehouses` | товар и склад остатка есть в справочниках |
| `stock.time_ignored` | `fetchStock($asOf)` — остаток на конец дня: время в `$asOf` не влияет |
| `stock.movements_balance` | остаток на конец диапазона = остаток на конец дня накануне + сумма движений диапазона (на этом стоят оборачиваемость и дни до обнуления). Только при обеих capability |
| `history.bounds` | только для адаптеров с `ProvidesHistoryBounds`: после `historyEnd()` нет сделок и движений |
| `<раздел>.error` | метод бросил исключение; остальные разделы проверяются дальше |

Правила для остатков и движений пропускаются (и перечисляются в выводе как
пропущенные), если адаптер не заявил соответствующую capability; так же
`history.bounds` — для адаптеров без `ProvidesHistoryBounds` (у реального
источника конец истории — «сейчас», это нормально).

## Чего проверка не ловит

Смысл данных: правильные ли суммы, те ли товары, не потеряны ли документы
в самом источнике. Это сверка с отчётами 1С/Б24 на стороне клиента.
