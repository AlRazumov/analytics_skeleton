# Проверка на Large-профиле мока (2026-09-26)

Пункт «проверка страниц на Large-профиле мока» из статуса `docs/roadmap.md`.
§1–4 — замеры до исправлений, §5 — что исправлено и замеры после.

## 1. Как мерилось

- Отдельная БД `perf` в Postgres Sail (dev-БД `laravel` с демо на Medium не
  тронута), миграции, расчёт за 12 месяцев 2025-09..2026-08.
- Разовые скрипты в `storage/app/perf/` (git-ignored): фазы расчёта,
  калькуляторы по отдельности, страницы через HTTP-ядро (второй запрос, после
  прогрева; число и время SQL — `DB::getQueryLog`).
- Large: 5 000 товаров, 5 складов, 48 продавцов, ~50 000 сделок в месяц.
  Для сравнения — те же замеры страниц на dev-БД (Medium, 500 товаров).

## 2. Расчёт `metrics:calculate`

| Фаза | Время | Пик памяти |
|---|---|---|
| reference:sync | 0,6 с | 30 МБ |
| calculate (485 819 записей) | 302 с | 795 МБ |
| delete + write в транзакции | 64 с | 1 160 МБ |

По калькуляторам (внутри calculate):

| Шаг | Время | Примечание |
|---|---|---|
| fetchDeals (665 000 сделок) | 12 с | массив сделок — 448 МБ |
| revenue, abc, xyz, sellers, lost_sales, categories | 0,3–1,3 с каждый | |
| dead_stock | 23 с | |
| **days_of_stock** | **241 с** | 12 месяцев × (fetchStock ≈ 16 с + fetchStockMovements окна ≈ 7 с) |

Выводы:

1. **Память — блокер.** Пик 1,16 ГБ, а `ANALYTICS_CALCULATE_MEMORY_LIMIT` по
   умолчанию 512M: на Large ночной расчёт упадёт по памяти (с лимитом 512M не
   запускался, вывод по замеренному пику). Основные потребители — все сделки
   диапазона в массиве (448 МБ) и все 485 тыс. записей в памяти до записи.
2. **days_of_stock — 80 % времени, но из-за мока, а не калькулятора.** Сам
   расчёт окна — ~0,2 с на месяц; остальное — MockAdapter, который при каждом
   `fetchStock()`/`fetchStockMovements()` заново проигрывает историю с начала.
   Для реального адаптера это те же 24 обращения к источнику за прогон (по два
   на месяц, см. `reports/stage-07-stock-metrics.md`) — при медленном API
   такая же проблема. Оценка «десятки минут» из отчёта этапа 07 не
   подтвердилась: 5 минут.
3. Запись 485 тыс. строк — минута; приемлемо для ночного расчёта.

## 3. Страницы

| Страница | Large | SQL (шт. / мс) | HTML | Medium |
|---|---|---|---|---|
| **/dashboards/overview** | **26 617 мс** | 15 / 697 | **7,7 МБ** | 2 427 мс, 659 КБ |
| /dashboards/abc-xyz | 932 мс | 4 / 25 | 7 КБ | 17 мс |
| /dashboards/transfers | 186 мс | 8 / 42 | 16 КБ | 20 мс |
| /dashboards/stock | 40 мс | 15 / 30 | 15 КБ | 21 мс |
| /dashboards/turnover | 31 мс | 10 / 18 | 16 КБ | 10 мс |
| /dashboards/top-products | 21 мс | 10 / 11 | 21 КБ | 22 мс |
| /dashboards/categories | 20 мс | 6 / 3 | 11 КБ | 21 мс |
| /dashboards/sellers (+ export) | 14–17 мс | 11 / 9 | 36 КБ | 11–13 мс |

N+1 нет ни на одной странице (число запросов не зависит от объёма).
Все страницы, построенные на `MetricsComparisonRepository` (сортировка и LIMIT
в БД), от объёма почти не зависят.

**Обзор** — единственная проблемная страница, уже на Medium 2,4 с. Разбивка на
Large:

| Виджет | Время | Почему |
|---|---|---|
| KPI выручки | 10,4 с | `WidgetDataProvider::sumFor()` читает все строки товаров за 12 месяцев (≈ 60 тыс. Eloquent-моделей) и суммирует в PHP |
| График выручки | 5,0 с | то же за 6 месяцев (30 тыс.) |
| Год к году | 5,2 с | то же, 6 + 6 месяцев |
| Таблица по товарам | 5,3 с + 0,5 с рендер | все пары товар × месяц — **29 988 строк** на странице |

SQL при этом — 0,7 с: время уходит на гидратацию моделей и сборку DTO.
ABC/XYZ (0,9 с) — та же причина в меньшем масштабе: 5 000 моделей ради
подсчёта 9 ячеек.

## 4. Что предлагается исправить

| # | Что | Эффект | Решение |
|---|---|---|---|
| 1 | Обзор: KPI, график и YoY — сумма по периодам в SQL (`SUM … GROUP BY period_start`, новый метод репозитория) | 20 с → десятки мс на Large | техническое |
| 2 | Обзор: таблица «по товарам» — ограничить (топ-N товаров по выручке за окно, «показано N из M») или заменить | 7,7 МБ → десятки КБ | **продуктовое**: какую таблицу показывать на обзоре |
| 3 | ABC/XYZ: подсчёт ячеек в SQL (`GROUP BY value_meta->>'abc_class', …`) | 0,9 с → мс | техническое, не срочно |
| 4 | Память расчёта: запись по частям (калькулятор → запись, без накопления всех записей) и/или поднять лимит по умолчанию | 1,16 ГБ → ~0,5 ГБ | техническое; быстрый вариант — лимит 2G, правильный — потоковая запись |
| 5 | days_of_stock: один `fetchStock()` на начало диапазона + один `fetchStockMovements()` на весь диапазон с прокруткой остатка по месяцам (как у оборачиваемости) | 241 с → ~30 с на моке; 24 обращения к источнику → 2 | техническое, заметно по объёму; можно отложить до реального адаптера |

Пункты 1–2 нужны до показа демо на больших данных и до реального клиента
уровня Large; пункт 4 — до включения ночного расчёта на таком клиенте.

## 5. Что исправлено (та же ветка)

| # из §4 | Сделано |
|---|---|
| 1 | `MetricsSnapshotRepository::sumsByPeriod()` — `SUM … GROUP BY period` в БД; KPI, график и YoY на обзоре читают суммы, а не строки |
| 2 | Таблица обзора — «Товары с наибольшей выручкой за окно»: топ `display.table_limit` (20) товаров по сумме за 6 месяцев, колонки — месяцы и итог, «Показано N из M», ссылка на «Топ товаров». Новый метод `topBySum()` (сортировка и LIMIT в БД), `WidgetDataProvider::table()` заменён на `topTable()` |
| 3 | `cellsByMeta()` — ячейки ABC/XYZ через `GROUP BY value_meta->>…` |
| 4 | `MetricsCalculationService::calculateInChunks()` отдаёт записи порциями (сначала всё по сделкам — после этого массив сделок освобождается; затем оборачиваемость, неликвиды, `days_of_stock` по месяцу — `DaysOfStockCalculator::calculateByMonth()`); `metrics:calculate` пишет каждую порцию сразу, в той же транзакции; писатель собирает INSERT по чанку. `calculate()` сохранён (тот же результат одним массивом, тест сверяет). Лимит памяти по умолчанию — `1G` |
| 5 | **Не делалось.** 80 % времени `days_of_stock` на моке — генерация самого мока; стоимость обращений реального источника неизвестна, а переделка задевает ядро метрик остатков. Open-пункт в `docs/roadmap.md` — решать с первым реальным адаптером |

Замеры после (Large, та же БД `perf`):

| | До | После |
|---|---|---|
| Пик памяти `metrics:calculate` | 1 160 МБ | 538 МБ (из них 448 МБ — массив сделок, контракт «один fetchDeals за прогон») |
| Время `metrics:calculate` | ~6 мин | ~6,5 мин (порционная запись идёт внутри транзакции расчёта) |
| /dashboards/overview | 26 617 мс, 7,7 МБ | 193 мс, 22 КБ |
| /dashboards/abc-xyz | 932 мс | 19 мс |
| остальные страницы | 15–190 мс | 15–185 мс (без изменений в пределах разброса) |

На Medium обзор был 2,4 с — теперь в пределах остальных страниц.
