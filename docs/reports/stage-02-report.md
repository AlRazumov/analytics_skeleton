# Отчёт: Этап 02 — MockAdapter

## Итог
MockAdapter реализован как потоковая реализация DataSourceAdapter,
без временных заглушек и без недостающих методов. Все три fetch*-метода
возвращают `Generator` (проверено тестом через `instanceof`), данные
воспроизводимы по `(profile, seed)`, дисбаланс-сценарий межфилиального
перемещения для Large-профиля присутствует и покрыт тестом. Контракт
`DataSourceAdapter`, спроектированный на Этапе 01, оказался достаточным
— ничего в нём не пришлось расширять под нужды MockAdapter.

## Созданные файлы

### Профиль масштаба
- `app/Adapters/Mock/MockDataProfile.php` — enum (`Small`, `Medium`,
  `Large`) с методами `productCount()`, `dealsPerMonth()`,
  `warehouseCount()`, `warehouseIds()`. Числовые значения помечены в
  докблоках как ориентировочные (клиент по 1С-направлению согласился
  на работу, но точных объёмов ещё не передал).

### Сезонность и аномалии (app/Adapters/Mock/)
- `SeasonalPattern.php` — интерфейс `multiplierForMonth(int $month):
  float`, расширяемый механизм (MockAdapter хранит `list<SeasonalPattern>`
  и перемножает множители всех паттернов).
- `NewYearSeasonalPattern.php` — единственная реализация на этом
  этапе: пик спроса ноябрь/декабрь/январь (множители 1.3/1.8/1.2,
  ориентировочные). Выбран как самый общеприменимый ритейл/B2B-паттерн,
  не завязанный на специфику конкретной отрасли клиента — обоснование
  зафиксировано в докблоке класса.
- `DemandAnomaly.php` — интерфейс `multiplierFor(productId, date):
  ?float`, заготовка для расширения набора видов аномалий.
- `SingleSpikeAnomaly.php` — единственная реализация: разовый
  пятикратный всплеск спроса (Out-движений) на один товар в один месяц.
  Товар и месяц выбираются детерминированно от `$seed` внутри
  `fetchStockMovements()` (первый месяц запрошенного периода).

### MockAdapter
- `app/Adapters/MockAdapter.php` — `implements DataSourceAdapter`,
  конструктор `(MockDataProfile $profile = Medium, int $seed = 42)`.
  - `fetchProducts()` / `fetchDeals()` / `fetchStockMovements()` —
    генераторы (`yield`), ничего не собирается в массив целиком.
  - Каждый fetch-метод создаёт собственный `Random\Randomizer` с
    `Random\Engine\Mt19937`, засеянный от `crc32($seed . ':' .
    $context)`, где `$context` — имя метода. Это даёт: (а) детерминизм
    при одинаковых `(profile, seed)`; (б) независимость методов друг
    от друга — вызов `fetchProducts()` не влияет на результат
    последующего `fetchDeals()`, что и требовалось докблоком
    `DataSourceAdapter` («реализация не должна кешировать состояние
    между вызовами»).
  - Продукты генерируются без привязки к складу — как и на Этапе 01,
    `Product` не менялся.
  - Движения склада (`In`/`Out`) генерируются по каждому складу
    профиля пропорционально `dealsPerMonth / warehouseCount`, с учётом
    сезонного множителя и разового всплеска аномалии.
  - `Transfer`-движения генерируются только когда `warehouseCount >
    1` (т.е. не на Small), используют пару `warehouseId` (from) /
    `toWarehouseId` (to) — по инварианту, добавленному в StockMovement
    на Этапе 01 (постфактум-правка от 2026-09-09). Доля Transfer от
    общего объёма движений склада — 5%, помечена как ориентировочная.
  - Дисбаланс-сценарий (пункт 7 из задания) реализован в приватном
    методе `imbalanceScenario()`: только для `Large`-профиля, только в
    первом месяце запрошенного периода, товар зафиксирован явно
    (`prod-1`), склады — первые два в списке `warehouseIds()` профиля.
    Величины (`5000` overstock / `4800` understock) намеренно взяты на
    порядок больше типичного фонового объёма движений по одному товару
    за месяц, чтобы сигнал был безусловно различим на фоне случайных
    движений — это и есть контракт для будущего алгоритма рекомендаций
    межфилиального перемещения.

### Тесты (tests/Unit/Adapters/MockAdapterTest.php)
- `returns a Generator from every fetch method` — типы возврата.
- `is reproducible for the same profile and seed` /
  `produces different results for different seeds` — воспроизводимость
  и зависимость от seed (первые 20 элементов).
- `keeps memory growth sub-linear for the large profile stock movement
  stream` — память после первых 10 элементов Large-потока сравнивается
  с памятью после полного прохода (~несколько тысяч+ записей);
  прирост не должен быть пропорционален объёму.
- `stops generating work early when the caller breaks out of the loop`
  — чтение первых 10 элементов Large-потока значительно быстрее
  полного прохода.
- `includes a warehouse imbalance scenario for the large profile` —
  net-движение `prod-1` по первым двум складам Large-профиля: явно
  положительное на одном, явно отрицательное на другом.
- `does not include the imbalance scenario for the small profile` —
  отсутствие `stock-imbalance-*` id на Small.
- `respects the Transfer/toWarehouseId invariant from Stage 01 across
  the stream` — для каждого `Transfer` `toWarehouseId` не null и не
  равен `warehouseId`; для остальных типов `toWarehouseId` — null.
- `does not generate transfers for the single-warehouse small profile`.
- `generates the profile-configured number of products`.

## Самостоятельные решения / отклонения от плана

**Проверка «не кеширует состояние между вызовами» реализована через
seed, производный от имени метода (`crc32($seed . ':' . $context)`),
а не через общий `Randomizer` на весь адаптер.** План этого явно не
требовал, но без этого одинаковый `$seed` давал бы одинаковую
последовательность чисел для `fetchProducts()` и `fetchDeals()`, если
вызывать их в разном порядке или не вызывать один из них вовсе —
результат бы менялся в зависимости от истории вызовов, что напрямую
противоречило бы докблоку `DataSourceAdapter` из Этапа 01. Отклонение
несущественное (в рамках «выбор реализации», не архитектурное
решение), но фиксирую, так как не было явно расписано в плане.

**Величины дисбаланс-сценария увеличены с изначально предполагавшихся
~500/480 до 5000/4800** — при продуктовом каталоге ~5000 и случайных
фоновых движениях по конкретному товару (`prod-1`) шум мог в редких
раскладах сравняться по порядку с сигналом на ~500. На порядок большие
величины делают тест на дисбаланс не зависящим от конкретного `$seed`.

**Доля Transfer-движений (5%) и пропорция `dealsPerMonth /
warehouseCount`** — собственные ориентировочные константы, не заданные
явно в задании; помечены в коде как таковые.
