# Этап 24: возвраты — нетто-логика калькуляторов — отчёт

## 1. Что сделано

Контракт разрешает отрицательные `Deal::amount` (возврат), и сделка с
положительной суммой — продажа. Отдельного признака возврата в `Deal` нет.
Калькуляторы теперь различают продажи и возвраты там, где это важно для
смысла метрики.

| Слой | Файл | Что |
|---|---|---|
| core | `Core/Analytics/LostSalesCalculator.php` | «В месяце были продажи» — есть сделка с `amount > 0`, а не нетто > 0. `value` — сумма продаж (без возвратов) ближайшего месяца с продажами |
| core | `Core/Analytics/AbcClassifier.php` | Накопление и общая сумма — только по товарам с нетто > 0, доля ≤ 1. Товары с нетто ≤ 0 получают C. `value` — нетто, как раньше (может быть ≤ 0) |
| core | `Core/Analytics/Sellers/SellerSalesData.php` | Число сделок и первый/последний день продаж — только по продажам, сумма — нетто |
| mock | `Adapters/MockAdapter.php`, `Mock/MockScenarioConfig.php`, `Mock/MockDataProfile.php`, `Mock/MockScenarioManifest.php` | Сценарий `returns` (`returnsCount`: Small 2, Medium 5, Large 10), факты — `manifest()->returnProducts` |

## 2. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Что такое продажа | сделка с `amount > 0`; сделка с нулевой суммой — не продажа и не возврат | признака возврата в `Deal` нет, знак суммы — единственное, что даёт контракт |
| Потерянные продажи: месяц, где продажи погашены возвратами | не «потерянный» | товар продавался; раньше нетто ≤ 0 делало месяц «потерянным» (п. 2.2 review) |
| Потерянные продажи: месяц только с возвратами | «потерянный» (если в горизонте были продажи) | продаж нет, возврат — не спрос |
| Оценка потери (`value`) | сумма продаж того месяца, без возвратов | это оценка спроса «сколько теряем в месяц». Нетто занижено возвратами продаж прошлых месяцев |
| ABC при отрицательных нетто | Парето только по товарам с нетто > 0, остальные — C | раньше отрицательные суммы уменьшали общий итог и доля лидера превышала 1 (A=100, B=−30 → 1,43 → C), а при итоге ≤ 0 все товары становились C (п. 2.3 review) |
| `value` у ABC | нетто без изменений | это «выручка товара за период», на неё опирается страница ABC/XYZ |
| XYZ | без изменений | CV считается по месячному нетто; отрицательный месяц — это изменчивость спроса, при среднем ≤ 0 — Z (так было и раньше) |
| Выручка по периодам и категориям, сумма продаж продавцов, доля | нетто, без изменений | выручка — это нетто |
| Число сделок, средний чек, продаж в активный день у продавцов | считаются только продажи | возврат — не сделка продавца. Иначе продажа с возвратом давала бы 2 сделки и средний чек 0, а поздний возврат продлевал бы активное окно уволенного продавца |
| Сценарий в моке без сдвига | товары `returns` идут после остальных сценариев, у их сделок отдельные потоки случайных чисел, обычные сделки не гасятся | без сделок сценария отпечаток сделок Small/Medium совпадает с прежним побайтно (`MockDealsWindowTest`). Движения товаров сценария — как у обычных |

### Сценарий `returns`

- Каждый месяц окна истории у товара есть гарантированная продажа
  (`deal-returns-<товар>-<Y-m>`) и, как у любого товара, случайные обычные
  сделки.
- В последнем месяце окна истории возвращаются все продажи месяца, и
  обычные, и гарантированная (`deal-return-<id продажи>`, тот же продавец,
  дата не раньше продажи). Нетто месяца 0, хотя продажи были.
- У каждого второго товара сценария в последнем месяце возвращается ещё и
  гарантированная продажа предыдущего месяца, поэтому нетто месяца
  отрицательное.
- `manifest()->returnProducts`: `productId => ['month' => 'Y-m', 'month_net' => float]`.

Что видно на демо: в последнем месяце у этих товаров выручка 0 или
отрицательная, и на «Топ товаров» они оказываются в начале анти-топа
«Наименьшая выручка среди проданных». Это правда о данных (продажи были, но
их вернули). «Потерянными» они не считаются.

## 3. Тесты

- `LostSalesCalculatorTest`: месяц с продажами, погашенными возвратами (нетто
  0 и отрицательное), — не потерянный; месяц только с возвратами — потерянный,
  оценка по продажам предыдущего месяца без возвратов; месяц только с
  возвратами в горизонте продажами не считается.
- `AbcClassifierTest`: при отрицательном нетто у части товаров доли считаются
  от суммы положительных нетто, отрицательные и нулевые товары получают C;
  при общем нетто ≤ 0 классификация остальных не ломается.
- `SellerMetricsTest`: число продаж, нетто, средний чек и продажи в активный
  день при возврате. Инвариант «сумма по продавцам = итог» теперь
  проверяется для числа продаж, а не для всех сделок.
- `MockReturnsTest`: факты manifest (продажи каждый месяц, нетто последнего
  месяца, возвраты только у товаров сценария и только в последнем месяце).
  Без сценария обычные сделки и движения не меняются. Товары сценария не
  «потерянные», товары `lost_sales` — «потерянные», как раньше.
- `MockDealsWindowTest` (slow): эталон переснят. Отдельно проверяется, что
  без сделок сценария отпечаток прежний.

`adapter:check` на моке (Medium) — нарушений нет. Полный прогон (включая
slow), Pint и PHPStan — зелёные.

## 4. Что осталось

- Признак возврата или тип документа в `Deal` — когда появится реальный
  источник. Если источник отдаёт возврат не отрицательной сделкой, а
  отдельным документом, адаптер должен привести его к отрицательной сумме.
- На стенде после обновления нужен `metrics:calculate`: на моке появятся
  возвраты, изменятся выручка и ABC товаров сценария за последний месяц.
