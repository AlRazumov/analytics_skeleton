# Этап 19: проверка контракта DataSourceAdapter — отчёт

## 1. Что сделано

- `App\Adapters\Contract\AdapterContractChecker` (+ `ContractReport`,
  `ContractViolation`): проверяет любую реализацию `DataSourceAdapter` на
  диапазоне — ~25 правил в разделах capabilities, справочники, сделки,
  продавцы, движения, остатки, границы истории. Только вызывает fetch*-методы
  и сверяет результаты; исключение из метода — нарушение `<раздел>.error`,
  остальные разделы проверяются дальше. Правила без нужной capability
  пропускаются и перечисляются.
- Команда `adapter:check [--period=YYYY-MM:YYYY-MM]` (по умолчанию три
  последних месяца; для мока — три последних месяца истории). Только чтение.
- Разбор `--period` вынесен из `metrics:calculate` в трейт
  `Console\Commands\Concerns\ResolvesMonthRange`; поведение `metrics:calculate`
  не менялось (его тест `CalculateMetricsResolvePeriodTest` не трогался).
- `docs/adapter-contract.md` — таблица правил для разработчика адаптера;
  ссылка в `CLAUDE.md`.

Живой прогон на dev (Medium, seed по `.env`): `deals: 14964, products: 500,
warehouses: 3, sellers: 24, movements: 31960, balances: 1500` — нарушений нет.

## 2. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где живёт проверка | `app/Adapters/Contract`, не в `tests/` | нужна и тестам, и команде для реального источника; зависит только от core-контракта |
| Как ловить «конец диапазона не включительно» | разрез по дню D, в котором есть записи: `[начало..D] ∪ [D+1..конец]` и выборка за `[D..D]` | разрез посередине диапазона не видит ошибку, если на границе нет данных (первая версия её пропускала — поймано тестом) |
| Остатки | `fetchStock(конец) = fetchStock(накануне начала) + Σ движений` по парам, допуск 1e-6 | на этом стоят оборачиваемость и дни до обнуления |
| Отрицательные суммы/остатки | не нарушение | возвраты; в 1С бывают отрицательные остатки — решать ядру, не контракту |
| Склад движения/остатка вне справочника | нарушение, только если справочник складов не пуст | контракт разрешает адаптеру не отдавать склады вовсе |
| Примеры | до 5 на правило, счётчик — все случаи | на реальных данных нарушений может быть тысячи |

## 3. Найденное расхождение: `SellerCoverage::Full`

Докблок enum говорил «Full — продавец у всех сделок», а мок в режиме `full`
по замыслу этапа 17 отдаёт ~7% сделок без продавца (виджет показывает строку
«Без продавца»). Первая версия правила `sellers.coverage` по докблоку уронила
мок. Код этапа 17 и виджет рассчитаны на поведение мока, поэтому исправлен
докблок (`app/Core/Domain/Enums/SellerCoverage.php`), а правило проверяет
только различимое по данным: `none` — ни у одной сделки нет продавца;
`full`/`partial` — продавец есть хотя бы у одной. Различие full/partial —
заявление источника (пометка о доле покрытия на дашборде).

## 4. Тесты

`tests/Unit/Adapters/Contract/AdapterContractCheckerTest.php` — 32 теста:
мок Small (full/partial/none) и Medium (slow) — 0 нарушений, 0 пропусков;
эталонный `Tests\Support\InMemoryAdapter` — 0 нарушений, пропущен только
`history.bounds`; без capabilities методы остатков не вызываются; сделки без
продавца при full допустимы; 21 заведомо сломанный адаптер ловится своим
правилом (диапазон, id, товар, NaN, тип, неповторяемость, конец не
включительно, покрытие, sellerId, справочник, capabilities, движения, остаток
без учёта asOf, остаток «на момент», дубль пары, исключение, данные после
historyEnd); после исключения проверка продолжается; лимит примеров.

`tests/Feature/CheckAdapterCommandTest.php` — 4 теста: мок проходит и ничего
не пишет в БД; сломанный источник — код 1, правило с числом случаев; период по
умолчанию для источника без границ истории; неверный `--period`.

Полный прогон (`sail artisan test`, включая slow): **520 passed (96 577 assertions)**,
180 с. До этапа — 484 / 96 487. `vendor/bin/pint --test` — чисто.
