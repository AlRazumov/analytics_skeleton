## 2. Часть A: детерминизм сделок

**Воспроизведение (seed 1, сделки июня 2026 при разных запросах; количество везде одинаково):**

| Профиль | месяц | квартал | вся история | диапазон с запасом (2024..2028) |
|---------|-------|---------|-------------|---------------------------------|
| Small (200 сделок) | 53089.40 | 50122.13 | 50068.77 | 50705.51 |
| Medium (5000 сделок) | 1274306.49 | 1286861.01 | 1257471.09 | 1257487.64 |

Через конвейер (seed 42 из config, Small): выручка июня при `metrics:calculate --period=2026-06:2026-06`
— 55484.46, при периоде по умолчанию (12 месяцев) — 50392.45.

**Решение.** Каждый календарный месяц окна имеет свой генератор `randomizerFor('deals:Y-m')`
и полное число сделок месяца; id — сквозной номер от первого месяца окна (`deal-N`, формат прежний).
Фильтр по запросу и по окну истории применяется к готовым сделкам по дате (границы включительно по
дню). Порядок: по месяцам, внутри месяца — порядок генерации (как раньше). Метод `monthsIn()` удалён
как ненужный.

**После правки (те же запросы):** июнь Small — 49428.80 при любом способе запроса; Medium —
1264938.55; конвейер (seed 42) — 48893.10 и для месячного прогона, и для 12-месячного.

**Количество и сумма сделок в окне (seed 1, запрос на всё окно):**

| Профиль | Сделок до → после | Сумма до → после | Разница |
|---------|-------------------|------------------|---------|
| Small | 2660 → 2660 | 667594.43 → 673591.97 | +0.9 % |
| Medium | 133000 → 133000 | 33693948.73 → 33558933.48 | −0.4 % |

Количество не изменилось (формула `dealsPerMonth × сезонность` та же, окно состоит из целых месяцев).
Сумма изменилась только из-за другого потока случайных чисел; средняя сумма сделки прежняя по порядку
величины (~250). Конвейер Small по умолчанию (seed 42): снэпшотов 2952 → 2949, строк revenue
594 → 591, сумма revenue 672766.86 → 673021.75.

**Эталонные константы (`MockDealsWindowTest`), запрос на всё окно, конец окна 23:59:59, seed 1:**

| | Small | Medium |
|---|---|---|
| было | 2660 / 667594.43 / `14427abb8b8bd9a4079ca1327f5d4f42a5ff98e8076751ef160dbaa823020220` | 133000 / 33693948.73 / `e972fecb7c8ddd9eca39bfb2b6038be258cac19537ec1f15fe31356d70f5450c` |
| стало | 2660 / 673591.97 / `19b9dfb71d06b2ffc6745841fb0eb68bd51168ea5b1955642bb70411ce0284b9` | 133000 / 33558933.48 / `cc47982e16e777ad1b83ebc2de9184eb6f8a572c2153b87748347443ffac1063` |

**Тесты** (`MockDeterminismTest`, `MockRevenueRangeIndependenceTest`): месяц, запрошенный месяцем /
кварталом / всей историей / диапазоном с запасом, даёт побайтно одинаковый набор сделок (Small — 4
месяца, Medium — 3 месяца в группе slow); нарезка по дням; сквозные id; детерминизм по seed (два
экземпляра одинаково, seed 7 и 8 по-разному); конвейер: `--profile=small` за месяц, за квартал и за
всю историю даёт одинаковую выручку месяца по всем товарам (допуск 1e-9); `fetchStockMovements`
целиком/с запасом/по месяцам и `fetchStock(asOf)` = сумме движений диапазона.

**Побочное следствие.** Раньше сделки последнего дня диапазона с датой без времени
(`DateRange(…, 2026-06-30)`) терялись; теперь границы включительно по дню, и конвейер видит весь
последний день.

## 3. Часть B: возраст неликвидов

- Возрасты: Small `[100, 250]`; Medium/Large `[100, 150, 250, 400]` циклически по номеру мёртвого товара.
  Итог: Small — prod-1: 100 дн. (последняя продажа 2026-05-23), prod-2: 250 (2025-12-24);
  Medium — 100, 150, 250, 400, 100 (даты 2026-05-23, 2026-04-03, 2025-12-24, 2025-07-27, 2026-05-23).
- **Правило ограничения** (`MockAdapter::deadAgeFor`): возраст ≤ глубина истории − 1 − 90 (у товара
  не менее 90 дней обычной истории до последней продажи; Small: 274, Medium: 639); больше — укорачивается.
  Возраст < 90 (порог неликвида по умолчанию) — `InvalidArgumentException`.
- Мёртвый товар живёт обычной жизнью до дня последней продажи (включительно), в этот день продажа
  гарантирована (со склада с максимальным остатком), списаний/корректировок после неё нет, дальше движений
  нет; остаток > 0 (после пополнения на каждом складе он не ниже точки заказа).
- **Манифест:** `deadProducts` (id → дата) сохранён, но теперь это дата ПОСЛЕДНЕЙ ПРОДАЖИ (совпадает с
  датой последнего движения); поле `deadDays` удалено, добавлено `deadAges` (id → дни на historyEnd).
  `MockScenarioConfig::deadDays` заменён на `deadAges`.
- Тесты (`MockDeadAgesTest`): по фактическим данным Small и Medium (slow): последняя продажа — в
  заявленную дату, после неё движений нет, остаток > 0, возраст ≥ 90 и равен `deadAges`, есть история
  (> 30 продаж) до неё; ограничение (900 → 274); ошибка при 50; изменение возрастов не трогает остальные
  товары. `DeadStockCalculator` по эталону манифеста (`MockStockMetricsTest`) остался: все deadProducts ≥
  порога, ложных срабатываний нет (seed 1, 2, 3).

## 8. Расхождения с заданием и решения

1. Дата в `deadProducts` — теперь дата последней продажи (прежде — последнего движения); у новых данных
   они совпадают.
2. Поле `deadDays` удалено (нигде больше не нужно), а не оставлено.
3. `chart.umd.min.js` вместо `chart.umd.js`: именно его отдаёт CDN по `chart.js@4`.
4. Словарь подписей применён в четырёх Blade-компонентах к любым заголовкам (не-метрики проходят по
   fallback без изменений), так как core отдаёт виджетам сырые ключи и менять его не требовалось.
5. Покрытие дефицита сделано 5–9 дней (≤ 10), излишка — 120–210 дней (≥ 90).
6. Сделки: границы диапазона стали включительными по дню (см. побочное следствие в разделе 2).
7. Тесты Medium — в группе slow, Large в Pest не запускался.

## 11. Замеченные проблемы вне скоупа

- Сделки не связаны с движениями: мёртвые товары и товары дисбаланса продолжают попадать в сделки
  (выручка есть и после последней продажи), а у товара с нулевыми продажами по движениям может быть выручка.
- Пары дефицита сценария 7 попадают в таблицу «Риск дефицита» демо (по порогу 14 дней) — ожидаемо, но
  меняет вид демо.
- В `MetricLabels` попали служебные названия колонок (`period`, `entity_id`); при появлении локализации
  словарь стоит перенести в языковые файлы.
- `metrics:calculate` по умолчанию на Medium считает 12 месяцев (без «года назад»); `demo:install` считает
  всю историю (решено на этапе 12).
- Large-профиль по-прежнему не гоняется в Pest, сценарий 7 на нём не проверялся.
