# Этап 27: индикатор свежести данных — отчёт

## 1. Что сделано

Над каждой страницей дашбордов (не на странице входа) — строка «Данные
рассчитаны 28.09.2026 06:02 за 2025-09 — 2026-08.» и, при необходимости,
жёлтое предупреждение.

| Слой | Файл | Что |
|---|---|---|
| БД | `2026_09_28_100000_create_metrics_runs_table.php`, `Models/MetricsRun.php` | журнал запусков: source, status, period_start/end, snapshots_written, error, started_at, finished_at |
| команда | `Console/Commands/CalculateMetrics.php` | строка `running` перед синхронизацией справочников; `success` с числом снэпшотов после транзакции; при исключении — `failed` с текстом ошибки (до 2000 символов), исключение пробрасывается дальше |
| presentation | `Services/DataFreshness.php`, `View/Components/FreshnessBar.php`, `components/freshness-bar.blade.php`, layout | последний успешный расчёт, более поздняя неуспешная/идущая попытка, «устарели» |
| config | `analytics.display.timezone` (`ANALYTICS_DISPLAY_TIMEZONE`, `Europe/Moscow`), `analytics.display.stale_after_hours` (`ANALYTICS_STALE_AFTER_HOURS`, 36) | `.env.example`, README |

## 2. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где хранить | отдельная таблица `metrics_runs`, а не `max(updated_at)` снэпшотов | нужен период расчёта и неуспешные попытки; снэпшоты этого не знают |
| Запись в транзакции расчёта или вне | вне: строка создаётся до, обновляется после | транзакция расчёта откатывается при сбое — запись о сбое в ней пропала бы |
| Какая попытка важна | только неуспешная/идущая, начатая позже последнего успешного расчёта | старый сбой, после которого расчёт прошёл, пользователю не интересен |
| Порог «устарели» | 36 ч от окончания успешного расчёта | ночной расчёт + запас: одна пропущенная ночь уже видна |
| Часовой пояс | время хранится в UTC (как приложение и планировщик), показывается в `Europe/Moscow` | клиенты — 1С/Б24 в России; настраивается |
| Текст ошибки на плашке | не показывается, только «завершился ошибкой» | это внутренняя информация; она в журнале и `storage/logs/metrics.log` |
| «Идёт расчёт», если процесс убит | остаётся `running`, плашка пишет «идёт расчёт (начат …)», плюс «устарели» по порогу | отличить убитый процесс от долгого без внешнего наблюдателя нельзя; порог свежести всё равно предупредит |
| Нет журнала (данные до этапа 27) | плашки нет | не выдумываем время расчёта; появится после первого `metrics:calculate` |
| Отклонённый до старта запуск (неверный `--profile`/`--period`) | в журнал не пишется | расчёт не начинался, данные не менялись |
| Где логика | `App\Services` + view-компонент, не core | журнал расчётов — инфраструктура приложения, к расчёту метрик не относится |

## 3. Тесты

`tests/Feature/DataFreshnessTest.php`:

- успешный `metrics:calculate` пишет запуск (источник `mock/small`, период,
  число снэпшотов = строк в `metrics_snapshots`);
- упавшая запись снэпшотов — запуск `failed` с текстом ошибки, хотя сам
  расчёт откатился; запуск, отклонённый до старта, не пишется;
- плашка: время в часовом поясе показа, период; старый сбой до успешного
  расчёта не показывается; сбой после — предупреждение «показаны данные
  предыдущего»; идущий расчёт и порог «устарели»; без журнала и на странице
  входа — ничего.

Полный прогон (включая slow), Pint и PHPStan — зелёные.
