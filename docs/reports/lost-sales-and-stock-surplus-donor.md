# Отчёт: две демо-эвристики из Known issues (потерянные продажи, донор без продаж)

Не новый этап (закрытие двух пунктов Known issues из `docs/roadmap.md`).
Обе реализации — ЭВРИСТИКИ ДЛЯ ДЕМО/ПРОДАЖИ ПРОДУКТА, не финальное
продуктовое решение: конфигурируемы, задокументированы как эвристика,
подлежат пересмотру при появлении реального клиента (этапы 15/16).

## 1. Потерянные продажи (`lost_sales`)

### Что сделано

- `App\Core\Analytics\LostSalesCalculator` (core, чистый расчёт над уже
  полученным набором `Deal` — `fetchDeals()` не вызывается повторно):
  товар считается потерявшим продажи в месяце M, если в M сделок нет, а в
  одном из `horizonMonths` предыдущих месяцев были. `value` — выручка
  ближайшего такого месяца (оценка «сколько теряем в месяц»), `valueMeta`
  — `horizon_months`, `last_sale_period`.
- Горизонт — `analytics.lost_sales.horizon_months` (по умолчанию 1),
  конфиг, не хардкод; биндинг в `AppServiceProvider` по образцу
  `DaysOfStockCalculator`.
- Метрика встроена в `MetricsCalculationService::calculate()` (тот же
  `$deals`, что у Revenue/Abc/XyzClassifier) и в реестр удаления/перезаписи
  `CalculateMetrics::METRICS` (`['product', 'lost_sales']`).
- ОГРАНИЧЕНИЕ задокументировано в докблоке класса: горизонт ищется только
  внутри запрошенного диапазона — у начала диапазона видимость уже, чем
  `horizonMonths`, что может занижать число найденных потерь у самого
  начала (не завышать: товар без единой видимой продажи в горизонте не
  помечается «потерянным»).
- Сценарий в `MockAdapter` (`lost_sales`, `MockScenarioConfig::$lostSalesCount`):
  отдельная от `seasonal` категория товаров — влияет только на `fetchDeals()`
  (не на остатки/движения). У каждого зарезервированного товара гарантированная
  сделка есть в каждом месяце окна истории, кроме последнего, а в последнем —
  ни одной (обычные случайные попадания туда тоже гасятся). Реализовано без
  изменения потока случайных чисел для остальных товаров и без сдвига
  нумерации `deal-N` (гарантированные сделки — отдельный id-неймспейс
  `deal-lost-{index}-{Y-m}`), поэтому byte-identical-тесты по другим месяцам
  не затронуты.

### Тесты

- `tests/Unit/Core/Analytics/LostSalesCalculatorTest.php` — прямые тесты
  калькулятора на синтетических `Deal` (флаг срабатывает, не срабатывает,
  разные горизонты, товар без продаж вообще не помечается, валидация
  `horizonMonths`).
- `tests/Unit/Adapters/MockLostSalesTest.php` — сценарий в `MockAdapter`:
  сделки есть во всех месяцах истории, кроме последнего; нет пересечения
  с `seasonalProductIds`; детерминизм независимо от диапазона запроса.

## 2. Донор без продаж (`stock_no_demand`, `TransferDonorReason::StockSurplus`)

### Что сделано

- `DaysOfStockCalculator` дополнительно пишет метрику
  `NO_DEMAND_STOCK_METRIC_KEY = 'stock_no_demand'` (entity_type
  `product_warehouse`) для пар, у которых `days_of_stock` не считается
  из-за отсутствия спроса (нет ни одной продажи в окне), но остаток на
  конец месяца положителен. `days_of_stock` не тронут — семантика «не
  пишется без спроса» сохранена полностью, это отдельная, узкая метрика.
- `App\Core\Transfers\TransferDonorReason` (enum: `Turnover`/`StockSurplus`)
  и `App\Core\Transfers\StockSurplusDonor` (productId, warehouseId, уже
  готовое к раздаче количество). `TransferRecommendation` получил поле
  `$reason` (по умолчанию `Turnover` — обратная совместимость с
  единственным местом создания рекомендаций).
- `TransferPlanner::plan()` принимает второй необязательный аргумент
  `$stockSurplusDonors`: такие доноры участвуют в раздаче наравне с
  обычными (тот же порядок по убыванию доступного количества), но не
  проверяются по `deficit_days`/`surplus_days`/`keep_days` (у них нет
  скорости продаж) — `fromCoverageBefore`/`fromCoverageAfter` для них
  условно `INF`. Пустой второй аргумент по умолчанию → поведение без
  вызова изменений не поменялось (подтверждено существующими тестами
  `TransferPlannerTest`, которые не передают второй аргумент).
- `TransferRecommendationService`: для товаров, у которых есть дефицитная
  пара (как и раньше), дополнительно читает `stock_no_demand` за тот же
  период (`MetricsSnapshotRepository::findByPeriodKeys`, добавлен как
  зависимость сервиса); склады с остатком выше
  `analytics.transfers.stock_surplus_min_stock` (новый конфиг, по
  умолчанию 20) становятся донорами «по остатку» с
  `reason=StockSurplus`.
- Сценарий в `MockAdapter` (`no_sales_donor`,
  `MockScenarioConfig::$noSalesDonorCount`): склад-донор получает один
  приход в начале истории и ни одной продажи за всю историю; парный склад
  — обычный дефицит того же товара (как у `imbalance`, но донор без
  единого движения типа Sale).
- Эвристика видна на странице «Перемещения»: `TransferRow` и
  `TransferTableProvider` пробрасывают `reason` в виджет
  `transfers-table.blade.php` — колонка «Донор» («по обороту» / «по
  остатку (без продаж)»), `INF`-покрытие донора без спроса показывается
  как «—», а не число.

### Тесты

- `tests/Unit/Core/Analytics/DaysOfStockCalculatorTest.php` — обновлены
  два теста, ожидавшие пустой результат при отсутствии спроса (теперь
  ожидают строку `stock_no_demand`), плюс новый тест на случай нулевого
  остатка (метрика не пишется).
- `tests/Unit/Core/Transfers/TransferPlannerTest.php` — новые тесты:
  обычный донор помечен `Turnover`; донор без спроса покрывает дефицит
  целиком (`reason=StockSurplus`, покрытие `INF`); дефицит делится между
  обычным донором и донором без спроса; донор без спроса с `available<=0`
  и товар без дефицита игнорируются.
- `tests/Feature/Transfers/TransferRecommendationServiceTest.php` —
  существующий тест «известного ограничения» переименован и оставлен
  как есть (без `stock_no_demand`-данных поведение не изменилось); добавлены
  тесты: донор выше порога включается (`reason=StockSurplus`, полное
  покрытие дефицита), донор на/ниже порога игнорируется, `stock_no_demand`
  для товара без дефицита игнорируется.
- `tests/Unit/Adapters/MockNoSalesDonorTest.php` — сценарий в
  `MockAdapter`: донор без единой продажи, дефицит на парном складе,
  остатки на конец истории совпадают с манифестом.

### Побочные правки существующих тестов (эталоны, не логика)

Добавление сценариев в `MockAdapter` намеренно меняет детерминированный
вывод мока, что потребовало пересчёта нескольких «эталонных» тестов
(логика тестов не менялась, только зафиксированные числа/хэши):

- `tests/Unit/Adapters/MockDealsWindowTest.php` — фингерпринт сделок Small/
  Medium пересчитан (гарантированные сделки lost_sales меняют количество/
  сумму/состав); старые числа оставлены в комментарии, как и было принято
  на этапе 13.
- `tests/Unit/Adapters/MockImbalanceTest.php` — тест «остальные товары не
  меняются без сценария [imbalance]» уточнён: индексы `no_sales_donor`
  теперь тоже исключены из сравнения (они, как и `imbalance`, занимают
  зарезервированный диапазон id и сдвигаются вместе с `imbalanceCount`).
- `tests/Feature/DemoInstallCommandTest.php` — ожидаемый список
  `metric_key` в БД дополнен `lost_sales` и `stock_no_demand`.
