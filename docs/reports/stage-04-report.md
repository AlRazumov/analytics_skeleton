# Отчёт: этап 04 — Расчётный пайплайн (adapters → metrics_snapshots)

## Что реализовано

**Калькуляторы** (`app/Core/Analytics/`) — один класс на метрику, каждый
принимает `DataSourceAdapter` (интерфейс) + `DateRange`, возвращает
`MetricsSnapshotRecord[]`. Импортов конкретных адаптеров нет — проверено
вручную и грепом (`grep -r "App\\\\Adapters" app/Core/Analytics` — пусто).

- `RevenueByPeriodCalculator` — revenue по (товар, месяц) из `fetchDeals`,
  `metric_key='revenue'`, `value_meta=[]`.
- `AbcClassifier` — A/B/C по кумулятивной доле выручки (Парето: первые
  80% — A, следующие до 95% — B, остаток — C). Один снэпшот на товар за
  весь период, `period` = последний месяц периода.
- `XyzClassifier` — X/Y/Z по коэффициенту вариации спроса по месяцам
  (X: CV≤10%, Y: CV≤25%, Z: CV>25%), популяционное std/mean.
- `TurnoverCalculator` — оборачиваемость по (товар, месяц): units sold /
  средний остаток месяца, на основе `fetchStockMovements`.

`AbcClassifier` и `XyzClassifier` пишут в общий `metric_key =
'abc_xyz_classification'`, каждый — только свою часть `value_meta`
(`abc_class` / `xyz_class`). Слияние в одну строку на товар происходит в
`MetricsCalculationService::mergeAbcXyz()`, а не в самих калькуляторах —
иначе один классификатор знал бы о существовании другого.

**`MetricsCalculationService`** (`app/Core/Analytics/`) — оркестрирует все
4 калькулятора над одним `DataSourceAdapter`+`DateRange`, возвращает
плоский список записей для записи. Не знает о точке входа (команда/Job) —
принимает только контракт адаптера, поэтому вызываема из чего угодно без
изменений.

**Write-контракт** — `app/Core/Widgets/Contracts/MetricsSnapshotWriter.php`
(`write(array $records): void`), отдельно от `MetricsSnapshotRepository`
(тот остался чисто read-only, как использует `WidgetDataProvider`).
Реализация `EloquentMetricsSnapshotWriter` (`app/Repositories/`) —
сериализует `value_meta` в JSON (`null`, если массив пуст, как в текущей
схеме) и пишет чанками по 500. Забинжена в `AppServiceProvider`.

**Artisan-команда** — `php artisan metrics:calculate {--profile=medium}
{--period=}` (`app/Console/Commands/CalculateMetrics.php`):
- `--profile`: `small|medium|large`, через `MockDataProfile::tryFrom()`;
  неверное значение — понятная ошибка (`Неверный --profile=...`), не
  краш.
- `--period`: `"YYYY-MM:YYYY-MM"`; неверный формат/начало позже конца —
  понятная ошибка. Без `--period` — последние 12 месяцев от текущей даты
  (дефолт для ad-hoc запуска).
- Инстанцирует `MockAdapter` напрямую (`new MockAdapter($profile)`) —
  единственное место в проекте, которое знает конкретный класс адаптера;
  сама расчётная логика (`MetricsCalculationService`) — нет.
- Перед записью удаляет существующие снэпшоты `entity_type='product'`,
  `metric_key IN (revenue, abc_xyz_classification, turnover)` за все
  месяцы запрошенного периода — повторный прогон не плодит дубли.

проекта "расчётные функции core — чистые unit-тесты на фиксированных

- `AbcClassifierTest` — пороги 80/15/5 на границе (кумулятивная доля

- `MetricsCalculationServiceTest` — слияние ABC/XYZ в одну строку на

  (см. ниже).

Тесты писались поверх уже реализованной логики, без её изменения;
реальных багов не найдено — все проверки подтвердили заявленное
поведение, включая допущения 1, 4, 5.

Итог: 44 теста (было 35 после stage-03), все зелёные.

## Defensive-проверка инварианта в mergeAbcXyz()

Добавлено отдельным дополнением после ревью: `mergeAbcXyz()` матчит
записи `AbcClassifier`/`XyzClassifier` по `entityId`, не по `period` —
это безопасно только пока оба классификатора кладут одинаковый
`period` (сейчас оба всегда используют последний месяц периода).
Раньше нарушение этого инварианта (например, если один из
классификаторов сменит гранулярность вывода) прошло бы молча: `period`
и `value` итоговой записи тихо взялись бы от `AbcClassifier`.

Теперь при расхождении `period` для одного `entityId` `mergeAbcXyz()`
бросает `RuntimeException` с именем товара и обоими значениями
`period` — нарушение становится громким, а не тихим искажением данных
в `metrics_snapshots`. Добавлен тест, воспроизводящий расхождение
через `ReflectionMethod` (реальные классификаторы сейчас всегда
согласованы, поэтому иначе кейс не собрать без переписывания их
логики). Итог после этого дополнения: 45 тестов.

## Прогон на всех профилях

Выполнено через `sail artisan metrics:calculate --profile=X
--period=2025-01:2026-06` для `small`, `medium`, `large` — все три
завершились без ошибок (`small`: 1235 снэпшотов, `medium`: 11390,
`large`: 114311). Демо-страница `/demo/widgets` отрендерена вручную через
`WidgetDataProvider` на данных из прогона — рендерится без ошибок на
`medium` (на `large` рендерится тоже, но даёт ~7.7 МБ HTML из-за таблицы
на 5000 строк — это ожидаемо для демо-виджета без пагинации, не баг
пайплайна). Финальное состояние БД после ручной проверки — данные
`--profile=medium`, как и указано в инструкции ниже.

**Вырождение XYZ-классов.** Во всех трёх профилях класс `X` не встретился
ни разу (только `Y`/`Z`, подавляющее большинство — `Z`):
- `small`: `{"AZ":38,"BZ":8,"CZ":4}`
- `medium`: `{"AZ":372,"AY":14,"BZ":79,"BY":4,"CZ":31}`
- `large`: `{"AZ":3770,"AY":111,"BZ":811,"BY":11,"CZ":290,"CY":7}`

Причина — не малый размер выборки (сохраняется и на `large`), а
`MockAdapter::fetchDeals()`: сумма сделки генерируется равномерно случайно
(`amount = randomizer->getInt(500, 50000) / 100`) независимо для каждой
сделки, без корреляции между месяцами. При таком распределении CV
помесячной выручки товара почти всегда получается высоким (что и
ожидается от честного расчёта вариации на данных без реального
сезонного/трендового поведения по товару — сезонность в
`MockAdapter` сейчас общая для всех товаров одновременно, не создаёт
разброс между товарами). Это свойство генератора мок-данных, а не
дефект `XyzClassifier` — при использовании реального источника
(Bitrix24/1С) распределение будет содержательным.

## Допущения (важно для приёмки)

1. **ABC — пороги Парето 80/15/5**, а не ранговые квартили прежнего
   seeder'а. Пороги — стандартный вариант ABC-анализа, не выведены из
   ТЗ или реальных данных клиента; подлежат пересмотру, когда появится
   реальная методология от продукта.
2. **XYZ — "спрос" = сумма `Deal::$amount` за месяц**, не количество
   единиц: в `DataSourceAdapter` нет поля "штуки" на сделку, только
   денежная сумма. Использована как единственный доступный заменитель
   объёма спроса.
3. **XYZ — все месяцы периода, включая месяцы без продаж (0)**, иначе
   товар с редкими крупными продажами выглядел бы стабильнее, чем есть.
   Population std (делитель N, весь период — не выборка).
4. **XYZ — при отсутствии продаж товара за весь период (mean=0)** CV
   математически не определён → товар относится к `Z` (нестабильно/нет
   спроса), а не отбрасывается из классификации.
5. **Turnover — методология не следует однозначно из контракта
   адаптера.** `DataSourceAdapter` не предоставляет абсолютный остаток
   на складе, только поток движений (`fetchStockMovements`). Выбрано:
   остаток товара — накопленное сальдо `In - Out` (Transfer между
   своими складами сальдо товара не меняет), начиная с **0 в начале
   запрошенного периода** (не абсолютный физический остаток на начало
   периода — его источник не даёт). Средний остаток месяца =
   `(opening + closing) / 2`; `turnover = unitsSold(Out) / avgStock`
   (в разах за месяц). Если `avgStock <= 0` — снэпшот за месяц не
   пишется (нет базы для деления, а не "оборачиваемость 0"). Ограничение:
   при ненулевом реальном остатке на начало периода первые месяцы будут
   занижать/искажать фактическую оборачиваемость — это внутренний
   недостаток относительного расчёта без стартового остатка, а не баг
   реализации; для реального источника (когда появится метод получения
   абсолютного остатка) методология потребует пересмотра.
6. **Слияние ABC/XYZ по товару** — `value` итоговой строки
   `abc_xyz_classification` берётся из `AbcClassifier` (суммарная
   выручка товара), `XyzClassifier`-значение (CV) в `value` не
   попадает — используется только `xyz_class` из его `value_meta`. CV
   как число нигде дальше не нужен (виджет читает только классы).

## Что не сделано / вне рамок этапа

- Job-обёртка над `MetricsCalculationService` — не запрашивалась ТЗ, но
  архитектурно подготовлена (сервис не знает о команде, может быть
  вызван из `Illuminate\Contracts\Queue\ShouldQueue`-класса без
  изменений в `core/Analytics`).
- Инкрементальный/дифференциальный пересчёт (сейчас — full recalculate
  за период с предварительным удалением) — не требовался.
- Абсолютный остаток на начало периода для `TurnoverCalculator` — контракт
  `DataSourceAdapter` его не предоставляет; при появлении такого метода
  расчёт потребует пересмотра (см. допущение 5).
